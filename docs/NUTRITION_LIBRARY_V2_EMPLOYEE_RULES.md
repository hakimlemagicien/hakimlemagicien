# قواعد موظف مكتبة التغذية — أساس نسخة V2

**الجمهور:** موظف التغذية / مدير مكتبة الوجبات  
**الغرض:** بناء مكتبة جديدة **بنفس نظام المنصة** حتى يبقى التعديل والتوسيع سهلاً لاحقاً  
**المفتاح الوحيد للهوية:** `external_id`  
**العقد الحالي في الكود:** Nutrition Data Contract **v1.1** — `schema_version: "1.1.0"`  
**المصدر التقني:** `src/lib/platform/meal-library.ts` + `public.meals` / `public.meal_ingredients`

هذا التقرير **لا يغيّر العقد**. أي قيمة جديدة خارج القوائم أدناه تحتاج موافقة مالك المنتج + مهندس القاعدة قبل الاستخدام.

---

## 1. المبدأ الحاكم

المنصة لا تنظّم الطعام بالاسم الظاهر ولا بالصورة ولا بهدف الكويز العربي.

تنظّمه بهذه الطبقات فقط:

| الطبقة | الحقل | ماذا يفعل |
|--------|--------|-----------|
| الهوية | `external_id` | مفتاح ثابت لكل وجبة في الكود، الصور، التخزين، القاعدة، البدائل، خطط العملاء |
| التصنيف الزمني | `meal_type` | فطور / غداء / عشاء / سناك / قبل التمرين / بعد التمرين / مشروبات |
| ملاءمة الهدف الغذائي | `suitable_goals` | خسارة دهون / ثبات / بناء عضل |
| السلامة | `allergens` | استبعاد البدائل حسب حساسية المستخدم |
| الاستبدال | `substitution_profile` | هل يجوز استبدال هذه الوجبة بوجبة أخرى |
| الحصة | `calories` + الماكروز + المكونات | قيمة غذائية لحصة واحدة فقط |

**قاعدة ذهبية:** غيّر الاسم أو الوصفة أو الصورة بحرية. **لا تغيّر `external_id` أبداً بعد الإنشاء.**

---

## 2. الهوية — `external_id`

### الشكل الإلزامي

```
MEAL-NNN
```

- بادئة ثابتة: `MEAL-`
- ثم رقم من **3 خانات** مع أصفار أمامية: `MEAL-001` … `MEAL-300` … ثم `MEAL-301`
- مثال صحيح: `MEAL-007`
- أمثلة مرفوضة: `MEAL-7` · `meal-001` · `MEAL_001` · `MEAL-001-V2` · `DRINK-001` · اسم عربي

### قواعد الموظف

1. كل وجبة لها `external_id` **فريد** في كل المكتبة.
2. التسلسل **متصل بلا فجوات** داخل الدفعة المعتمدة (`MEAL-001` ثم `MEAL-002` …).
3. `external_id` **لا يتغير** إذا تغيّر الاسم العربي أو الإنجليزي أو المكونات أو الصورة.
4. لا تُعاد استخدام هوية وجبة مؤرشفة لوجبة جديدة.
5. لا تُنشأ هوية موازية (`MEAL-001-V2`). التعديل يتم **على نفس السجل**.
6. التوسيع المستقبلي = متابعة الرقم التالي (`MEAL-301+`). تغيير شكل المعرّف بعد `MEAL-999` قرار معماري، ليس قرار موظف تغذية.

### أين يظهر نفس الـ ID

| المكان | المسار |
|--------|--------|
| سجل الوجبة | `"external_id": "MEAL-001"` |
| صورة المصدر | `images/MEAL-001.png` |
| صورة التسليم | `public/nutrition/meals/MEAL-001/cover.webp` |
| المصغّرة | `public/nutrition/meals/MEAL-001/cover-thumb.webp` |
| التخزين المستقبلي | `meals/MEAL-001/cover.webp` |
| خطة العميل / البدائل | نفس `MEAL-001` |

إذا اختلف أي مسار عن الـ ID، الوجبة **مرفوضة**.

---

## 3. ما يُمنع وضعه على سجل الوجبة

سجل المكتبة **كتالوج** فقط.

يُمنع إضافة أي من:

- `completed` / `skipped` / `current`
- تاريخ أكل المستخدم
- تقييم المستخدم
- رقم حصة مخصّصة لعميل معيّن
- حالة الخطة اليومية

حالة المستخدم تعيش في طبقة الخطة/التعيين، لا على وجبة المكتبة.

## 4. أنواع الوجبات — `meal_type`

القيم المسموحة في المنصة (snake_case فقط):

| القيمة في الملف / القاعدة | العرض العربي |
|---------------------------|--------------|
| `breakfast` | الفطور |
| `lunch` | الغداء |
| `dinner` | العشاء |
| `snack` | سناك |
| `pre_workout` | قبل التمرين |
| `post_workout` | بعد التمرين |
| `drinks` | مشروبات |

### قواعد صارمة

- لا Title Case: ممنوع `Breakfast` أو `Lunch` في ملف التشغيل.
- لا قيم تسويقية: ممنوع `Drinks / Nutritional Add-ons`.
- **المشروب = `drinks` فقط.** ممنوع إعادة تصنيفه كـ `snack` أو `pre_workout` أو `post_workout` حتى لو يُشرب قبل/بعد التمرين.
- لا تُخترع أنواع جديدة (`dessert`, `smoothie`, `supplement`) بدون تغيير رسمي للعقد + enum القاعدة.
- البديل يطابق **نفس** `meal_type`. فطور لا يُستبدل بغداء.

### توزيع المكتبة الحالية (مرجع تناسق 300 وجبة)

يُحترم هذا الميزان عند بناء دفعة جديدة بنفس الحجم، ما لم يصدر توزيع رسمي جديد:

| النوع | العدد |
|-------|------:|
| `breakfast` | 55 |
| `lunch` | 70 |
| `dinner` | 60 |
| `snack` | 40 |
| `pre_workout` | 25 |
| `post_workout` | 30 |
| `drinks` | 20 |
| **المجموع** | **300** |

كل نوع يحتاج كثافة كافية حتى يجد محرك البدائل مرشّحين من نفس النوع.

## 5. أهداف التغذية — `suitable_goals`

هذه **ليست** أهداف الكويز (`fat`, `muscle`, `athletic`…).  
هذه أهداف غذائية داخل المكتبة فقط:

| القيمة | المعنى |
|--------|--------|
| `fat_loss` | خسارة الدهون |
| `maintenance` | ثبات / محافظة |
| `muscle_gain` | بناء العضلات |

### قواعد

- المصفوفة مصفوفة نصوص snake_case فقط.
- الوجبة قد تناسب هدفاً واحداً أو أكثر.
- في المكتبة الحالية **كل الوجبات تحمل `maintenance`**. هذا نمط معتمد: الثبات هو القاعدة، ثم يُضاف `fat_loss` و/أو `muscle_gain` حسب الماكروز.
- الترتيب داخل المصفوفة لا يغيّر الهوية، لكن يُفضَّل نمط ثابت: `fat_loss` ثم `maintenance` ثم `muscle_gain`.
- المنصة ترتّب نتائج `fat_loss` تصاعدياً حسب السعرات، و`muscle_gain` تنازلياً حسب البروتين.

### ربط سريع مع أهداف الرجال في الكويز (للموظف فقط — لا تُكتب في سجل الوجبة)

| هدف الكويز للرجل | سلة المنصة | هدف التغذية المناسب عادةً |
|------------------|------------|---------------------------|
| `fat` خسارة الدهون | cut | `fat_loss` (+ `maintenance`) |
| `muscle` بناء العضلات | bulk | `muscle_gain` (+ `maintenance`) |
| `gain` زيادة وزن صحي | bulk | `muscle_gain` (+ `maintenance`) |
| `fitness` / `athletic` / `shape` | fitness | غالباً `maintenance` وقد يُضاف أحدهما حسب السعرات |

لا تضع في `suitable_goals` قيم الكويز (`fat`, `cut`, `bulk`, `تنشيف`).

---

## 6. الوسوم الغذائية — `dietary_tags`

قيم مستخدمة ومعتمدة اليوم:

- `vegetarian`
- `vegan`
- `pescatarian`
- `gluten_free`
- `high_protein`
- `high_fiber`
- `omega_3`

قواعد:

- snake_case إنجليزي فقط.
- الوسم يجب أن يطابق المكونات فعلياً. لا تضع `vegan` على وجبة فيها زبادي.
- `gluten_free` يتعارض مع وجود غلوتين في `allergens`.
- المصفوفة الفارغة مسموحة إذا لا ينطبق وسم.
- لا تُخترع وسوم جديدة (`keto`, `halal`, `low_carb`) بدون اعتماد قائمة رسمية.

---

## 7. مسببات الحساسية — `allergens`

القاموس الرسمي في المنصة:

| القيمة | العربي |
|--------|--------|
| `milk` | حليب |
| `egg` | بيض |
| `gluten` | غلوتين |
| `fish` | سمك |
| `tree_nuts` | مكسرات |
| `sesame` | سمسم |
| `soy` | صويا |
| `peanuts` | فول سوداني |
| `shellfish` | محار |

### قواعد V2 الإلزامية

- استخدم هذه المفاتيح **حرفياً**.
- ممنوع: `eggs` · `tree nuts` · `Dairy` · `غلوتين` داخل المصفوفة.
- الحساسية تُشتق من المكونات، لا من التخمين التسويقي.
- مثال ثابت في الاختبارات: البرغل → `gluten`.
- بعد أي تعديل مكونات يجب **مراجعة الحساسية وتأكيدها** قبل الحفظ (`allergens_review_required`).
- المصفوفة الفارغة تعني: لا حساسية معروفة من القائمة. لا تكتب `"none"`.

## 8. الحساب الغذائي (حصة واحدة)

### الأساس

- كل القيم لحصة واحدة (`yield_servings = 1`).
- كميات المكونات = الوزن **الصالح للأكل** بالجرام (أو مل للسوائل حيث ينطبق).
- المصدر المعتمد: **USDA FoodData Central** — أغذية عامة، ليس تحليلاً مخبرياً لعلامة تجارية إلا إذا ثُبّت FDC ID.
- تحجيم المكوّن: `قيمة_100غ × الوزن_غ ÷ 100`.
- السعرات المنشورة من الماكروز:

```
calories = protein_g × 4 + carbs_g × 4 + fat_g × 9
```

- حقل `qa` يحتفظ بمقارنة طاقة المكونات مقابل طاقة الماكروز:
  - `ingredient_energy_kcal`
  - `macro_energy_kcal`
  - `macro_formula`: `"protein_g*4 + carbs_g*4 + fat_g*9"`
  - `macro_vs_ingredient_delta_pct`
- مرجع الجودة الحالي: أعلى فرق طاقة في المكتبة ≈ 11%. هدف الدفعة الجديدة: الإبقاء تحت هذا السقف، والأفضل أقرب إلى 5%.

### وحدات

| الحقل | القيم المسموحة |
|-------|----------------|
| `serving_unit` | `g` أو `ml` |
| وحدة المكوّن | `g` أساساً؛ `ml` للسوائل فقط |
| العرض للمستخدم | `غ` / `مل` — الواجهة تترجم، المصدر يبقى `g`/`ml` |

أرقام موجبة فقط. `serving_size > 0`. لا سعرات أو ماكروز سالبة.

---

## 9. المكونات — `ingredients`

كل مكوّن سجل مستقل:

| الحقل | القاعدة |
|-------|---------|
| `ingredient_order` | يبدأ من 1 ويتسلسل بلا فجوات |
| `ingredient_key` | مفتاح إنجليزي صغير ثابت (`oats`, `chicken`) — لا يُكرَّر داخل نفس الوجبة |
| `name_en` | اسم إنجليزي وصفي (حالة الطهي إن لزم: dry / cooked / drained) |
| `name_ar` | اسم عربي **مختلف** عن الإنجليزي — ترجمة حقيقية |
| `quantity` | أكبر من صفر |
| `unit` | `g` أو `ml` |
| `kcal` / `protein_g` / `carbs_g` / `fat_g` | قيم المكوّن لهذه الكمية |
| `source` | عادة `USDA FoodData Central` |
| `source_query_url` | رابط بحث FDC لنفس الاستعلام |

قواعد:

- لا مكوّن بلا `ingredient_key`.
- لا تكرار لنفس `ingredient_key` داخل الوجبة.
- الصورة يجب أن تعكس **قائمة المكونات هذه** لا قائمة تزيينية.
- خطوات التحضير بالعربية والإنجليزية خاصة بهذه الوصفة. ممنوع قالب عام مثل:  
  `Prepare the listed ingredients using the stated cooking method; combine and serve.`

## 10. عقد الاستبدال — `substitution_profile`

المنصة تستبدل وجبة بوجبة أخرى فقط إذا تحقق **الكل**:

1. ليست نفس الوجبة (`external_id` مختلف).
2. نفس `meal_type` (`meal_type_required: true`).
3. فرق السعرات ≤ **10%**.
4. فرق البروتين ≤ **8 غ**.
5. لا تتعارض حساسيات المرشّح مع حساسيات المستخدم (`exclude_allergens: true`).
6. إن لم يوجد مرشّح آمن: **لا بديل** — لا يُخترع بديل خارج العقد.

قيم ثابتة تُكتب على كل سجل:

```json
{
  "meal_type_required": true,
  "max_calorie_delta_pct": 10,
  "max_protein_delta_g": 8,
  "exclude_allergens": true
}
```

### نطاقات مساعدة (للتصنيف لا للمحرّك)

المحرّك يستخدم النسب أعلاه، لا اسم النطاق. النطاق يُملأ باتساق:

**سعرات `calorie_band_kcal`**

| القيمة | متى |
|--------|-----|
| `under_300` | أقل من 300 |
| `300_449` | 300–449 |
| `450_599` | 450–599 |
| `600_plus` | 600 فأكثر |

**بروتين `protein_band_g`**

| القيمة | متى |
|--------|-----|
| `under_20` | أقل من 20 |
| `20_29` | 20–29 |
| `30_39` | 30–39 |
| `40_plus` | 40 فأكثر |

**كربوهيدرات / دهون:** `low` · `moderate` · `high`

لا تغيّر نسب الاستبدال (10% / 8 غ) من طرف الموظف.

## 11. الصور

### ثلاثة ملفات لكل ID

| الدور | المسار | من يراه المستخدم |
|-------|--------|------------------|
| أصل PNG | `nutrition-library/batches/.../images/MEAL-NNN.png` | لا |
| غلاف تسليم | `public/nutrition/meals/MEAL-NNN/cover.webp` | نعم (التفاصيل) |
| مصغّرة | `public/nutrition/meals/MEAL-NNN/cover-thumb.webp` | نعم (البطاقات) |

في السجل:

```json
"image": {
  "reference": "images/MEAL-NNN.png",
  "status": "ready",
  "alt_ar": "<اسم الوجبة العربي>",
  "alt_en": "<English meal name>"
},
"image_status": "ready"
```

### قواعد الصورة

- مرجع الصورة = `images/{external_id}.png` حرفياً.
- صورة واحدة لكل وجبة. لا مشاركة ملف بين هويتين.
- لا نص / شعار / علامة مائية على الصورة.
- لا صورة عامة أو placeholder إذا `status=ready`.
- الصورة تُولَّد من **قائمة المكونات الكاملة والكميات النسبية وشكل التقديم وطريقة التحضير**.
- إن ظهر في الصورة طعام غير موجود في المكونات → رفض (سابقة: خس/خبز غير مدرج).
- الواجهة **لا تحمّل** ملف PNG الأصلي.

حالات `image_status`: `placeholder` · `ready` · `missing` · `review_required`  
للنشر: `ready` فقط.

## 12. حالات السجل

| الحقل | القيم |
|-------|--------|
| `status` | `pilot` · `published` · `archived` |
| `review_status` | نص مراجعة (تاريخ/جهة). النشر الإنتاجي يحتاج اعتماد اختصاصي تغذية مسجّل |
| `is_active` | في القاعدة فقط — المكتبة الظاهرة للعميل = النشط |

`status=pilot` **لا يعني** اعتماداً إنتاجياً.

## 13. الحقول الإلزامية لكل وجبة

نسخة V2 لا تُقبل بدون:

- `external_id`
- `name_ar` + `name_en`
- `description_ar` + `description_en`
- `meal_type`
- `suitable_goals`
- `dietary_tags` (يجوز `[]`)
- `allergens` (يجوز `[]`)
- `calories` · `protein_g` · `carbs_g` · `fat_g`
- `serving_size` · `serving_unit` · `yield_servings`
- `ingredients[]` منظمة
- `preparation_steps_ar[]` + `preparation_steps_en[]`
- `preparation_time_minutes`
- `image` + `image_status`
- `status` + `review_status`
- `notes`
- `substitution_profile`
- `qa`

حزمة JSON:

```json
{
  "schema_version": "1.1.0",
  "generated_on": "YYYY-MM-DD",
  "nutrition_basis": "USDA FoodData Central generic foods; one serving per record",
  "meals": [ ]
}
```

## 14. كيف تُوسَّع المكتبة دون كسر النظام

1. حدّد نطاق ID قبل الكتابة (`MEAL-301` → `MEAL-XXX`) ولا تتخطّى أرقاماً «للاحتياط».
2. سلّم **دفعة مغلقة**: سجلات + صور أصل + غلاف webp + مصغّرة + mapping + عقد + تقرير QA + manifest.
3. انسخ الدفعة إلى `nutrition-library/batches/{start}-{end}/`.
4. لا تعدّل هوية وجبة قديمة لملء نوع ناقص؛ أضف وجبة جديدة بالرقم التالي.
5. عدّل وجبة قائمة بـ **نفس** `external_id` (upsert). خطط العملاء المرتبطة تبقى صحيحة.
6. أرشفة وجبة = `status: archived` / `is_active: false`، ليس حذف ID من التاريخ.
7. لا تخلط حالة المستخدم مع الكتالوج.
8. لا تغيّر `meal_type` لوجبة لها بدائل/تعيينات إلا بمراجعة أثر الاستبدال.

### مخرجات الدفعة المطلوبة (كما في SOURCE)

- Meal Records  
- Master Images  
- Image Mapping  
- Contract-compatible data  
- QA Report  
- Manifest  
- Final Package  
- Copy into `nutrition-library/batches/`

## 15. بوابة الجودة قبل التسليم

يجب أن تمرّ الدفعة بهذه الفحوصات:

- عدد الوجبات = نطاق ID المعلن
- تسلسل `MEAL-NNN` متصل وفريد
- كل `image.reference` = `images/{external_id}.png`
- لا صور مكررة أو يتيمة
- كل `image_status` = `ready` ومعه `cover.webp` + `cover-thumb.webp`
- أسماء المكونات عربي ≠ إنجليزي
- خطوات تحضير خاصة بالوجبة باللغتين
- لا حقول حالة مستخدم على السجل
- `meal_type` من القائمة السبعية فقط، snake_case
- `suitable_goals` من الثلاثي فقط
- `allergens` من القاموس الرسمي فقط
- `substitution_profile` بالنسب 10% / 8 غ
- السعرات من معادلة 4/4/9
- المشروبات `drinks` وليست سناك

مرجع الاختبار الآلي الحالي: `src/lib/platform/meal-library.test.ts`.

## 16. ما لا يفعله موظف التغذية

- لا يغيّر شكل `external_id` أو يعيد ترقيم مكتبة قديمة.
- لا يضيف نوع وجبة جديد أو هدف جديد من تلقاء نفسه.
- لا يعيد ترميز المشروبات كسناك/قبل/بعد التمرين.
- لا يضع أهداف الكويز أو أهداف الرجال (`fat`, `cut`, `تضخيم`) داخل `suitable_goals`.
- لا يستخدم صورة لا تطابق المكونات.
- لا يكتب قيماً Title Case في ملف التشغيل.

## 17. تعارضات يجب إغلاقها داخل V2 (لا تكرارها)

هذه فجوات المكتبة الحالية. نسخة V2 تُبنى **بدونها**:

1. ملفات العقد القديمة ما زالت تذكر أنواع الوجبات بـ Title Case وتُسقط `drinks`. التشغيل يستخدم snake_case + `drinks`.
2. بعض السجلات القديمة تستخدم `eggs` و `tree nuts` بدل `egg` و `tree_nuts`. V2 تعتمد القاموس الرسمي فقط.
3. واجهة الأدمن ما زالت قد تُسقِط `drinks` من قائمة الأنواع — السجل نفسه يجب أن يحمل `drinks`.
4. خطة العميل الافتراضية حالياً 4 خانات فقط (فطور/سناك/غداء/عشاء). ذلك طبقة خطة، لا يبرّر حذف `pre_workout` / `post_workout` / `drinks` من المكتبة.
